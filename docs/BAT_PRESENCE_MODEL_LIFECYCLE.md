# Bat-presence recogniser lifecycle and DOC domain-adaptation benchmarks

**Status: Approved objective and proposed implementation, NOT installed or tested in the owner's BatDailyTool/RT firmware.**  Recorded 2026-11-08.  Supersedes the local machine-short-tailed exclusion and long-tailed-only BMP target in the earlier planning text of issue #14.  Coordinates with #13 and #27.  This document is a design contract, not evidence of a working retraining scheduler.

## Agreed objective

Primary binary target: **IS BAT?**  Minimise missed genuine bat recordings while keeping false positives and review burden low.  Record bat presence, source provenance and uncertainty independently of species identity.  A second-stage species classifier is optional and must use genuinely human-verified species labels.  DOC Bat Batch 01 grades are *bat presence only*; the owner did **not** verify long-tailed versus short-tailed identity.

### Label precedence

- For owner-collected data with trustworthy, source-hash-bound human FastReview evidence: grades 1/2 = non-bat; grade 3 = uncertain (excluded from binary supervised training); grades 4/5 = bat present.  **Ignore machine-added short-tailed species tags for binary classification and eligibility; do not discard an otherwise good human-graded recording merely because of a machine species tag.**  Preserve the raw tag in provenance/audit history, but do not use it as a label or negative exclusion.
- If two independently confirmed human annotations genuinely conflict, quarantine/adjudicate rather than silently prefer either.  Artificial playback, corrupt/missing media, non-matching annotations, unresolved source origin and duplicated media have explicit handling and exclusion reasons.
- DOC: owner FastReview grades are bat/no-bat presence only.  DOC's independently human-verified short-tailed species labels may be retained as *separate* species metadata, with provenance and any disagreement recorded.  DOC automatic species labels do not become ground truth.
- Review changes supersede old labels in a **new versioned dataset snapshot**, never by mutating prior frozen snapshots.  Ambiguous legacy/automatic-only sidecars are not hard negatives.

## Lifecycle: Daily Run -> model candidate -> independent evaluation -> promotion review

1. **Observe (every completed Daily Run)**: ingest only reconciled, idempotent, human-graded new/changed reviewed BMP and paired WAV evidence.  Inventory event includes stable source identity, SHA-256 of media and annotation, grade, reviewer/provenance, original UTC recording night, collection/site, recorder, modality, source bandwidth, and eligibility reason.  Do not let a machine score or DOC machine species tag silently become a human grade.  Record last-successful-scan time and incomplete processing separately.
2. **Compare against the last *training snapshot***, not merely the 2026 Phase 1 audit and not just the active deployed model.  Count unique newly eligible positive and negative **media hashes** and distinct nights; track corrected/revoked reviews as separate invalidation events.  Suppress duplicate card imports, aliases, paired recorders of the same audio where acoustically confirmed, and repeated identical media.
3. **Readiness gate**: starting configurable candidate threshold proposal for BMP: at least **20 new bat-positive**, **100 new reviewed negatives**, and **5 distinct new nights** since last successful trained snapshot (retains existing provisional UI defaults).  Add at least a 14-day configurable cooldown, complete source-health checks, no unresolved integrity conflicts, and sufficient diversity monitoring by recorder/site.  These are provisional engineering triggers **not** statistical sample-size guarantees.  WAV has its own cohort and preliminary thresholds (existing planning defaults: 10 positive, 50 negative, 5 nights), reviewed independently.  Large grade corrections, new input-format support or deliberate manual request can request an audit/retrain even if count threshold is not met.  Nothing happens merely because the raw number of BMPs grows.
4. **Queue candidate training only after Run Daily completes and releases its lock**.  Never run compute-heavy fitting inside the daily ingestion/review lock.  An opt-in, separately scheduled Windows training worker consumes an immutable `train_request.json` from an atomic queue and records RUNNING/COMPLETE/FAILED, retry safety and resource/time limits.  Training failure does not disrupt Daily Run or RT monitoring.
5. **Freeze dataset versions before fitting**: binary target policy version, media hashes, review-sidecar hashes, source/night/site splits, negative-sampling strategy, DOC licensing/provenance decisions, code/dependency revision and random seed.  Preserve all raw reviews and older model artifacts.  Group near duplicates and recordings from correlated nights/sites, and exclude validation/test material from fitting or preprocessing statistics.
6. **Train parallel candidates on exactly matched local data**: local-only logistic baseline, local-only MLP (optionally CNN), then an otherwise comparable hybrid that adds a **separate human-labelled DOC training partition**.  Control all architecture/features/hyperparameters and local splits across corresponding arms.  Test capped or weighted DOC mixing (e.g. 0%, 10%, 25% of training weight; these are experiments, not deployment policy) to prevent domain dominance.  Do not import DOC data into Shed, South or normal Daily Run review counts.  Keep desktop BMP and RT-compatible WAV models separate.
7. **Evaluation ledger**: score *every new candidate once per named immutable cohort and threshold policy*.  Compare local-only versus hybrid on exactly the same untouched local new-night/site holdout(s), frozen DOC holdout cohorts and dedicated hard-negative challenge set.  Also calculate retrospective training/archive fit metrics explicitly labelled non-independent.  Report uncertainty intervals, denominators, recall, precision, specificity, FP per 1,000 candidate recordings, false alarms per healthy recorder-night when available, calibration, and per-site/recorder/BMP orientation/source-bandwidth performance.  Preserve per-recording predictions and both source/model hashes.  Never silently rerun old registered metrics after annotation changes.
8. **DOC train/test firewall**: maintain a permanent assignment ledger by source key + SHA-256, site/recorder/night and near-duplicate grouping.  Draw multiple frozen random *evaluation* cohorts independently, and geographically stratified cohorts when possible; use a separately human-verified DOC **training/adaptation** pool for hybrid models.  No DOC item may appear in both training and evaluation for a candidate.  Repeated tuning on an external benchmark turns it into development data.  The already-examined 46 DOC diagnostic examples can remain a historical comparison; if reused for DOC adaptation, mark them as training/dev and evaluate on new sealed DOC cohorts only.  Keep random prevalence-representative samples and positive/hard-negative enriched cohorts separate in reporting.
9. **Model report & recommendation**: generate a signed/hash-identified model card and structured report (`candidate_report.json`, `model_comparison.csv`, `per_recording_predictions.csv`, site/error breakdowns, threshold/ROC-PR curves, data provenance).  Compare with the currently approved model on the same cohort, mark differences with uncertainty and flag regression.  Candidate states: `ready_to_train`, `training`, `trained`, `evaluation_blocked`, `evaluated`, `rejected`, `approved_for_shadow`, `approved_for_active`, `rolled_back`.  Display pending examples since last snapshot on dashboard.
10. **Promotion requires explicit owner approval**.  A BMP desktop model can be promoted to offline/AviaNZ-side *only after* its matching loader and input contract are proven.  It is **not** a drop-in replacement for the RT WAV MLP.  For RT: separately verify exact WAV sample rate, feature extraction, exported/quantised weights, desktop-vs-device score parity, memory, latency/power, event recall and false-alert burden on held-out live recordings.  Begin in **shadow mode**, preserve the existing trigger and WAV capture, run unattended field comparison, then propose active promotion with atomic known-good rollback.  No automated firmware flashing or active-model swaps.

## Recommended report layout

- Training readiness: unique new grade 4/5, grade 1/2, grade 3, corrected reviews, new nights/sites, excluded/conflicted, and remaining-to-trigger.
- Candidate lineage: source manifest hash, model weight hash, feature/preprocessing SHA, library/toolchain versions, training window, positive/negative counts, DOC mixture and all evaluation cohort IDs.
- One table per **same cohort** comparing incumbent local-only, candidate local-only and candidate hybrid, with TP/FN/FP/TN, recall, precision, FP/1000, confidence intervals and decision threshold.  Separate site/format and challenge-set tables.
- Decisions and rollback: `do not deploy`, `keep collecting`, `approve desktop candidate`, `RT shadow trial proposed`, `RT shadow passed`, `RT active candidate proposed`, with reasons.  Never let one dashboard accuracy figure alone authorize promotion.

## Acceptance tests

1. Re-running unchanged Daily Run adds zero new examples; an added legitimate review increments once; alias duplication does not; changed human grade invalidates/versions old training evidence.
2. Machine-labelled short-tailed annotations on owner recordings cannot change a trusted human grade 1/2 to exclusion or grade 4/5 to 'uncertain'; human-verified DOC species metadata stays separate.
3. No training process can start while Daily Run is running or alter reviewed `.bmp.data`, backed-up machine metadata, source BMP/WAV, Shed-only activity outputs, or the RT active firmware.
4. Train/validation/test and local/DOC partitions are non-overlapping by media hash and correlated group; independent-test claims fail closed if provenance or overlap cannot be verified.
5. Repeated candidate runs from an identical frozen dataset/configuration are idempotent; candidate evaluation snapshots are append-only, with independent vs developmental status explicit.
6. A hybrid candidate never gets an advantage from DOC recordings it is tested against; all compared models use identical cohorts and denominator definitions.
7. RT promotion is impossible without a matching deployable WAV model, score parity, shadow results and explicit approval; rollback restores the prior active model.
