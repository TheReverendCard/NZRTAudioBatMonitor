# Trap and bait monitoring over MeshCore

**Design note, 25 November 2026.**  The proposed first trial uses a sleeping XIAO ESP32-S3 / Wio-SX1262 trap node and an internet-connected MeshCore receiver.  The receiver submits trap records to Trap.NZ.  The heartbeat temperature, trap-event firmware and receiver bridge are proposals awaiting a hardware trial and provider access.  [Trap and bait workstream #53](https://github.com/TheReverendCard/NZRTAudioBatMonitor/issues/53) · [Wildlife repeater workstream #9](https://github.com/TheReverendCard/NZRTAudioBatMonitor/issues/9)

## Heartbeat temperature on a sleeping trap node

Include a chip-temperature sample in each scheduled trap heartbeat.  After a long deep sleep the chip has had time to cool, so its temperature on waking is a plausible proxy for local thermal conditions.  It measures the ESP32-S3 silicon.  Enclosure temperature, sunlight, recent wake activity and charging can all affect its relationship to outside air.  This hypothesis applies to the trap role.  Continuous acoustic processing or repeater operation has a different thermal history.  [Espressif temperature sensor](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/peripherals/temp_sensor.html)

- Take the first valid reading as early as the firmware permits after waking, before radio transmission, Wi-Fi time synchronisation or other substantial work.  Reuse the sample in the heartbeat, so it costs no extra wake or radio packet.  Record chip temperature in °C, time awake at sampling, preceding sleep duration when known, and wake reason.  Flag cold boots, short sleeps and invalid readings so the receiver can interpret them.
- Retain the source as `chip_temp_c` in the project data.  The receiver can include the labelled proxy in the optional Trap.NZ `extra` field once the mapping is agreed.  Use the standard `temperature` field for a measured air temperature, or for an explicitly agreed proxy mapping that retains its provenance.  A missing reading can be omitted and the heartbeat can still be sent.  [Trap.NZ sensor record fields](https://api2.trap.nz/docs)
- Compare paired readings from a deployed enclosure and a nearby shaded, ventilated reference thermometer across day and night, long sleeps and repeated wake-ups.  Report bias and spread by wake history and sun exposure before claiming an ambient accuracy or applying a correction.

The trap role would wake for switch changes, time checks, reporting and optional scheduled receive windows.  A radio that is asleep misses packets sent during that interval.  Test coordinated receive windows and a sender retry or queued handoff before relying on a sleeping trap to relay messages.  Use an awake repeater where the route requires continuous availability.  Measure delivery rate, latency and battery cost for each role.  [ESP32-S3 sleep and wake sources](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/system/sleep_modes.html)

## MeshCore messages and the Trap.NZ receiver

| Purpose | Proposed behaviour |
| --- | --- |
| Read current state | Expose the reed switch as a digital input and battery voltage where measured through MeshCore Get Telemetry (`0x03`).  Configure which switch position means set for each installation.  Evaluate sensor-node subscriptions (`0x08`) for receivers that can renew them. |
| Record a transition | Persist each debounced state change before sending a typed MeshCore group datagram.  Include format version, stable sensor identity, event ID that survives restart, original event time and clock validity, event type and relevant readings.  Retry using the same event ID.  Ordinary repeaters forward the packet.  Receiving applications interpret its contents. |
| Submit to Trap.NZ | An authorised receiver maps the sensor to its installation and submits `sensor_id`, `date` and `event` through authenticated HTTPS `POST /sensorRecords`.  Use `Set`, `Sprung`, `Heartbeat` or `Baitlevel` as appropriate.  Preserve the event time through backhaul outages.  Keep credentials at the uploader and verify the originating device before posting.  A group datagram supplies neither sender identity nor event time by itself. |
| Recover missed events | Give receivers a shared persistent queue keyed by sensor and event ID.  Track receipt and Trap.NZ acceptance separately.  Reconcile an ambiguous API timeout before replay where possible.  A possible follow-up for MeshCore is a generic binary request for events after the receiver’s last stored ID. |

The wildlife overlay pins MeshCore repeater v1.18.0.  At that revision the companion has a group-datagram send command and the repeater handles telemetry queries.  This establishes source support.  The trap payload, replay, provenance and receiver handling still need end-to-end verification on the selected builds.  [Wildlife overlay](https://github.com/TheReverendCard/NZRTAudioBatMonitor/blob/7e8f3181844d0fee4200c8f771b4163f7d920ff9/firmware/meshcore_wildlife/README.md) · [Pinned companion source](https://github.com/meshcore-dev/MeshCore/blob/81dbae592ffad40b4212bc0b37e82b38da08f4bc/examples/companion_radio/MyMesh.cpp) · [Pinned repeater source](https://github.com/meshcore-dev/MeshCore/blob/81dbae592ffad40b4212bc0b37e82b38da08f4bc/examples/simple_repeater/MyMesh.cpp) · [Telemetry requests](https://github.com/meshcore-dev/MeshCore/blob/main/docs/payloads.md) · [Group datagrams](https://docs.meshcore.io/companion_protocol/)

Prototype in MeshCore’s development range (`0xFF00–0xFFFF`).  Once demonstrated, publish the format and decoder and propose a permanent application ID through a PR to `docs/number_allocations.md`.  One conservation-monitoring application ID could cover trap, bait and acoustic event types.  The Trap.NZ bridge would consume the supported trap and bait events.  [MeshCore allocation process](https://docs.meshcore.io/number_allocations/)

A separate native LoRaWAN option remains useful for groups with an existing Trap.NZ-connected gateway.  It requires a provisioned Class A OTAA endpoint, a matching AU915-2 or AS923-1 gateway and a decoder.  The proposed MeshCore-to-HTTPS pilot requires sensor-provider access and an associated sensor, and can use the existing internet connection at the receiver.  [Trap.NZ deployment guide](https://help.trap.nz/books/public-access-lorawan-network-service/page/deployment-information) · [Provider reference application](https://help.trap.nz/books/trapnz-comprehensive-user-guide/page/integrating-lorawan-sensors-with-trapnz)

## First field check

Use one reed-switch node and two receivers.  With the upload path offline, spring and reset the trap, restart the node, restore connectivity and replay the retained events.  Verify one correctly timed record per transition on the intended test trap, including when both receivers hear the same packet.  Check a heartbeat against the reference thermometer, confirm its temperature source is visible, and record missed relay opportunities during sleep.  Record results against [issue #53](https://github.com/TheReverendCard/NZRTAudioBatMonitor/issues/53).
