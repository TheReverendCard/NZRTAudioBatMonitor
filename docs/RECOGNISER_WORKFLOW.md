# Bat Monitor recogniser release workflow

Design status: proposed 6 November 2026. This document defines roles, evidence and release behaviour. It is not a firmware release. The XiaoSD periodic update is a separate, completed workstream.

## Desktop: keep the installed stock recogniser as the control

| Route | Input | Candidate processing |
|---|---|---|
| Stock NZ Bats | Native AR4 BMP and XiaoSD-derived BMP, reported separately | Installed AviaNZ NZ Bats unchanged; fingerprint executable, filter config and model weights |
| Custom BMP | BMP | Locally tuned pulse/pass rules |
| Custom BMP + NN | Same BMPs | Same pulse proposals plus learned classifier |
| Custom WAV | Original audio, or verified lossless decode | Direct waveform/spectrogram pulse/pass rules; a new AviaNZ bat route |
| Custom WAV + NN | Same audio | Same WAV proposals plus learned classifier |

The control for a WAV is the stock result on its derived BMP when available. Never describe this as native stock WAV inference. Preserve parent hashes and timing in the WAV/BMP mapping. Compare versions of rules alone vs the same rules with NN so their contributions are measurable. If experimenting with different proposal stages, version those separately. Log candidate intervals, gate decisions/rejections, per-class NN scores and final pass decisions. The stock result may be file-level only; do not invent pulse timestamps for it.

Run Daily archives stock outputs and receipts before review or experiments. Immutable stock snapshots include original annotations, recogniser hashes and run provenance. The fast review GUI writes an independent reviewer-labelled overlay keyed to recording/segment; labels include positive, explicit negative and unknown, with reviewer and confidence grade. Do not overwrite stock or infer expert verification from an AviaNZ certainty. For Jesse Card's `clear_bat_calls` labels, use an initial training sample weight of 0.85, adjustable per example within 0.8–0.9; use 1.0 for a trained bat ecologist's annotation. Store reviewer reliability separately from the label and AviaNZ certainty. The current target is local long-tailed bat calls, so these labels support bat-call detection and do not by themselves establish species identification. `Don't Know` remains unlabelled and is excluded from positive and negative supervised training. Include weak, ambiguous, machine-negative and scheduled clips in the review queue to expose missed calls. Give each experimental route private working sidecars and output directories. No experimental failure should erase the stock run.

Start with one shared library for audio features/scoring, replay CLI, test fixtures and fast review GUI in this repository. Use an AviaNZ fork, pinned to a known upstream commit, only for changes needed to its input handling, recogniser dispatch or results UI. A separately named filter may not activate the hard-coded bat path. Keep fork patches small; ship a compatibility manifest recording upstream commit/build, adapter version and preprocessing. Check applicable code, model and dataset licences before redistributing weights. A branch is a development workspace; publish immutable, versioned release assets for users/devices.

## Training and release states

Daily collection contributes reviewed examples, not daily automatic threshold changes. Link same-pass derivatives across recorders and keep them in the same night split. Respect [training issue #14](https://github.com/TheReverendCard/NZRTAudioBatMonitor/issues/14): uncertain/short-tailed/mixed or artificial examples are excluded from the local long-tailed natural-training target (do not turn them into negatives). Keep a retention/exclusion manifest. A periodic without a stock detection is a weak negative only. Preserve the distinction between acoustic correspondence and a biological label.

A configurable retraining trigger should check new independent reviewed passes, explicit negatives, nights, classes and recorder coverage since the previous training manifest. A pile of duplicate snippets does not satisfy it. Set initial thresholds from label accrual and uncertainty; they are not validated constants yet. Run an immutable train/validation/test split plus a prospective evaluation on newly collected nights. Compare recordings and matched-pass recall, false alerts per monitored hour/night, review burden and missing coverage. Report denominators and small-sample uncertainty by recorder and site. Record thresholds chosen on validation; do not repeatedly tune using the frozen test set.

Separate **latest candidate**, **active**, and **previous known-good**. Publish candidates to GitHub with version, content hash, model/input/preprocessing contract, label list, threshold, data manifest, permitted uses, runtime requirements and evaluation. Updating the candidate never promotes it automatically. Record the validation evidence, promotion decision and rollback target. The existing BMP and WAV joblib baselines are benchmarks, not AviaNZ recognisers or device binaries.

## Embedded: one reporting service, initially two acoustic paths

Goal: high-recall real-time bat activity plus NZ bird species identification on battery, reported over WiFi or LoRa. Aim for near-complete detectable passes in the deployment envelope, and report uncertainty and unmonitored intervals. Evaluate the species checklist explicitly; no all-NZ claim based on global model label count alone. Distinguish bat-pass detection from verified species identification.

Keep high-rate bat acquisition; derive an anti-aliased audible stream for birds if the microphone's audible response passes a field test, otherwise add a separate audible mic. An audio recogniser can consume small streaming spectrograms; no BMP files need to be made on the device. Keep a low-cost sensitive proposal stage, learn on short windows, aggregate to passes and audit independent scheduled windows for missed proposals. Benchmark S3 INT8 vector kernels and BirdNET-Tiny Forge first, not a full desktop CNN. Do not sleep the microphone while claiming continuous bat coverage. A battery budget must include sensing, compute, radio and idle/standby, using 24-hour wall time despite a USB meter pausing in sleep.

Test the WAV baseline in PC replay before a small CNN. On RT, measure inference latency, max queue depth, dropped blocks, input gaps, memory, recall and wall-clock Wh/day. On SD, also measure interference with recording/uploads. RT and SD must have separate capability profiles; models may require different binaries/front ends. The recovered [JOURNAL-2 source](https://github.com/TheReverendCard/NZRTAudioBatMonitor/pull/16) is not a complete reproduced build. Preserve current acquisition, RT-SCORE-1 and WiFi journal behaviour.

Future model updates: on WiFi in maintenance windows, fetch a signed manifest and verified compatible artifact into an inactive slot; verify digest, shape, operators, memory and known-input self-test. Keep the active model bootable through power loss, record install outcome, and retain rollback. Separate model-only updates from firmware changes required for new operators or preprocessing. Run both versions in shadow on identical windows where resources allow; where they do not, use logged replay or separate co-located devices and say so. Promotion requires adequate reviewed passes/negatives, recall and false-alert criteria, reliable capture and acceptable power, not just elapsed time. Roll back on failures.

Persist compact events before transmission with device/session/event ID, UTC or unsynced uptime, model version, score, monitoring health and delivery state. Send low-latency alerts by configured WiFi/LoRa route; retry opportunistically with receiver-side deduplication. Keep bounded journal retention, explicit loss counters and a watermark of acknowledged events. WiFi/Bluetooth field retrieval should export records since a cursor and work without internet. Do not count radio transmit as gateway delivery. The current daytime WiFi journal uploader is a useful existing mechanism; live alerting, Bluetooth retrieval and model OTA in this design are future capabilities.

## First implementation milestone
Read-only PC replay: same reviewed corpus and provenance; five desktop routes; separate AR4 and converted BMP summaries; per-record disagreements and candidate-stage traces; identical WAV baseline as a reference for future device replay. Build/benchmark rules-only routes before adding NN reranking, then test in Run Daily in parallel with stock. No device changes needed for this milestone.
