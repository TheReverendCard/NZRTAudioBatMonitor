# GUARD-2:  protect capture while testing higher-recall RT detectors

**Bench candidate, 14 November 2026 NZDT.**  This is the next RT firmware after the owner’s successful GUARD-1 build.  No supplied command flashes a device.  It does not change the SD recorder, Run Daily, downstream MLP weights, or the field unit by itself.  [GUARD-1 history](GUARD1-HISTORY.md).

## Build and try it

1. Extract the entire ZIP.  Double-click **Build GUARD-2 Bench Only.cmd**.  The default source is the configured PASS-1 project under your home directory.  To use the GUARD-1 folder you just built, in PowerShell from the extracted folder run:  
   ```powershell
   & ".\Build GUARD-2 Bench Only.cmd" --project "C:\Users\revje\NZRTAudioBatMonitor-meshcore\GUARD1_Bench_20261113T200748635881Z"
   ```
   All five inputs must match one known revision.  The builder creates a separate private `GUARD2_Bench_…` folder, compiles with PlatformIO, and writes `guard_build.log` and `guard_build_receipt.json`.  Keep private binaries, settings and logs on your PC.  The release contains no site credentials or owner firmware binary.
2. After a successful build, use the candidate on a supervised bench XIAO with the production microphone and radio.  Use your normal PlatformIO board upload for the **new** project if you choose to flash.  Leave the reference SD/AR4 and field unit unchanged during the bench.  In automatic daytime standby the detector is off; use the existing one-hour bench mode and confirm the log says monitoring.  With WAV enabled, run the same known call and background through the legacy baseline and then through assist, using the same gain and position.  Use ultrasonic-capable playback or a controlled PCM replay; laptop speakers cannot reproduce the full bat band.
3. Use **serial** on the candidate to select `nzrt pass assist evolved off`.  Check `nzrt pass status` for `version=PASS-2 active=evolved shadow=off assist=1`.  Selection takes effect at a safe analysis boundary after calibration; a requested setting alone is not proof.  The applied selection is persisted separately so GUARD-1/PASS-1 retains its previous preference on rollback.  Restore normal legacy behaviour on GUARD-2 with `nzrt pass legacy off`.  The existing downstream MLP shadow/active and WAV controls remain separate from first-pass controls.
4. For WiFi selection only, the optional_receiver folder contains a compatible launcher and controls for the published PASS-1 receiver layout.  Keep your current receiver for uploads if using USB to select assist.  To try the optional launcher, close the old receiver, start **Start_GUARD2_Receiver.cmd**, then **WiFi_GUARD2_Controls.cmd**, option 11, active `assist evolved`, shadow `off`.  Uses existing settings and tokens.  Don’t overwrite an independently updated receiver.  This optional launcher has not been tested on your Windows installation.
5. Log a continuous 30-minute loaded run **per profile**, taking `nzrt status` during each.  Exercise radio, journal and WAV uploads.  Validate the assist run with `py -3 bench_acceptance.py serial.txt --assist evolved`.  It requires microphone/DSP progress, no rising drop/gap counts, linked event/journal/WAV ACK, an event hit by the selected detector, and at least 95% ready selected windows across health samples.  The 95% is a proposed bench floor; review every gap.  Separately disconnect/reconnect WiFi and confirm journal recovery.  Inspect received WAVs.  Only then try an overnight, co-located comparison:  report reviewed AR4 passes with verified RT coverage as a separate denominator, additional waveform-reviewed RT hits, and background alerts per monitored hour.  Keep periods without evidence of listening as unknown.
6. Rollback:  use the previously built original project or the known private firmware image for that board.  The builder does not erase the filesystem or touch preferences.  No settings migration to an older firmware is needed.

## What changed

* Legacy still computes on each calibrated 20 ms window.  In ordinary selected mode a healthy new first pass decides independently.  In assist mode a positive from **either** legacy or the selected first pass can trigger an event.  A shadow never triggers by itself.  This is a collection policy for finding candidates; a trigger is not a bat identification.
* Both active and shadow feature calculations now share a 5 ms target per window.  The active rule runs first.  The evolved band bank checks the deadline between 240-sample pieces; the audible FFT checks within its recursion and butterfly loops.  Heavy work is skipped if the queue is at least half full or the existing repeated-gap hold is active.  After a budget overrun a selected rule sits out the next four eligible windows, a heavy shadow the next 250.  Legacy covers skipped, partially evaluated or warming selected windows.  A completed positive subwindow can still be used.  The guard is cooperative:  a scheduling pause, DMA loss, calibration, scoring, or reporting can still cause coverage loss.  There is no promise of a hard 5 ms wall-time bound.
* Short skips reset evolved filter delay without throwing away all the background estimates.  Longer skips (>50 consecutive skipped windows) or actual DMA discontinuities re-warm the affected rule.  The audible detector now packs the real samples into a 480-point complex FFT and reconstructs only the needed powers of the original 960-point spectrum.  Same rates, thresholds and bins.  Scratch drops by 3,840 bytes; no silicon speed or battery gain claimed.
* Existing GUARD-1 supervision, bounded restart, safe legacy recovery and local journal remain.  Healthy saved policies are honoured; installing the image does **not** silently opt a unit into assist.  After a supervised recovery, optional work is locked as in GUARD-1.

## Reading the journal

| Evidence | Interpretation |
|---|---|
| `first_pass`, `assist`, `trigger_mask` | Selected profile, union enabled, actual contributing rules across hot windows (bits:  1 legacy, 2 evolved, 4 audible).  Example:  3 = legacy and evolved contributed during the bout, possibly on different windows. |
| `fallback=1` | At least one window during this event had incomplete selected evaluation, possibly during the event tail.  Not proof that legacy alone started it. |
| `shadow_complete=0` | Shadow off, warming, or incomplete.  Absence of a shadow hit in that interval is unknown. |
| `new_ready`, `fallback_windows` | Lifetime since-boot counts of fully evaluated, warmed selected windows versus windows covered by legacy when a new active first pass was not fully ready.  Initial shared legacy calibration, DMA gaps, skipped audio and time asleep are outside this denominator. |
| `new_only`, `legacy_rescue`, `over_budget` | Counts of windows in which the selected rule hit with legacy cold, legacy retained a hit the selected rule did not make, and heavy calculations that reached the time budget.  These are not counts of individual bats. |
| `X-First-Pass` on WAV | Profile selected at trigger time.  Use the journal for the actual contributing rule(s), joined by session/run/sequence. |
