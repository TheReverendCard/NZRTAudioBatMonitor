# RT GUARD-1: protect primary detection and reporting

**Bench firmware candidate based on the exact five PASS-1 sources. No installer in this directory flashes a device or changes its saved configuration.**  Use a spare unit for the first on-board test.  The previous 13-profile emulator result was a recogniser equivalence test; this release tests firmware progress separately.

## Behaviour

| Failure | Candidate action |
|---|---|
| DSP input queue at least half full, recurring input gaps during existing clip hold, or an optional first-pass calculation consumes at least 5 ms | Skip optional evolved/audible shadow work; after an expensive calculation hold it off for 250 analysis windows (5 s of post-warmup processed audio). Keep executing the selected active trigger. Reset only the skipped shadow's history on resumption. A skipped interval increments shadow_skipped; a candidate covering an incomplete shadow comparison reports shadow_complete=0. Consumers must treat an incomplete comparison with no hit as unknown. No change to thresholds. The inexpensive legacy shadow can reuse the existing legacy result. |
| Reader, DSP block completion, or eligible detector windows stop advancing for 30 s while monitoring | A separate FreeRTOS task checks progress every second. It records the failure in RTC memory and requests one software restart. No requirement to hear bats or receive a network ACK to prove life. |
| Reporting loop stops making progress for 180 s, or optional initialisation after the supervisor starts never completes | Same bounded recovery. A receiver outage alone is not a reason to restart. |
| Recovery boot | Legacy activity detection first, first-pass shadow off, downstream MLP and WAV work bypassed. Core live candidate metadata and bounded journal queues remain. Saved user preferences are preserved. A subsequent fault stays reported without repeatedly restarting. A full power cycle restores the normal settings. Day standby and explicit DSP-off are excluded; decode-only bench does not require detector-window progress. |

Fault codes: 0 healthy, 1 no full microphone reads, 2 no DSP blocks completed, 3 no finished eligible analysis windows, 4 reporting or guarded startup stalled. Health and serial status expose guard_online, current and retained fault, safe mode and skipped optional windows. If the supervisor itself cannot be allocated, monitoring continues and the hardware gate rejects guard_online=0. One already-running expensive window cannot be preempted by this change. Expensive **active** scoring is preserved until an actual stall; set active=legacy for the initial test. Baseline detection may still lose data on an overloaded or failed board.

## What was verified

- The five files under base/ reconstruct the PASS-1 source overlay. Their newline-normalised SHA-256s match the published release recipe. They contain no site configuration header. prepare_build.py rejects any other revision and prepares an independent private build tree. The pinned bench scoring header is the recovered RT-SCORE-1 reference, not proof that every header on the owner's PC is identical.
- Native C++ and an ESP32-S3 guest both passed 898 assertions on the candidate detector/policy. Tests cover deliberate first-pass pressure, primary detections, unknown shadow results, quiet disconnected operation, standby, DSP diagnostic mode, counter wrap, and reader/DSP/window/reporter stalls. A second S3 guest ran the actual supervisor task, induced a DSP stall, called the real esp_restart(), validated the retained reason after reboot, and verified that a repeated stall did not reboot again. The fault injector advances a test clock; these aren't latency measurements. See evidence/emulator.json.
- The first S3 boot of the reconstructed detector exposed a coprocessor exception in a global floating-point constructor. GUARD-1 initialises filter/scorer state from task context and passes the same boot test. That diagnostic result does not establish the cause of an overnight field gap.
- Added a GitHub Actions workflow for qualifying changes on this branch and downstream branches carrying the workflow. It fails if the emitted detector or reset proof is missing. Branch protection / required checks must be set by a maintainer if bypass is to be prohibited. No changes were made to repository administration.
- Not tested here: complete owner-specific Arduino 2.x/MeshCore integration, real DMA/radio scheduling, SD, power, coverage while rebooting, or all filesystem/network failure paths. A dead CPU, scheduler or blocked interrupts can also prevent the new software supervisor from running. Existing hardware/RTOS watchdogs remain separate. A reboot can lose unsent RAM data; this is recovery, not uninterrupted coverage.

## Owner test

1. Extract the zip and run **Build GUARD-1 Bench Only.cmd**. Optional argument: `--project "C:\path\to\current\RT\project"`. It checks the five input hashes, builds a new sibling directory with PlatformIO and writes guard_build.log and guard_build_receipt.json there. The private build includes local settings; do not upload the build folder or binary. The original PASS-1 tree and deployed board stay as they were. A source rejection means another version is in use and needs a rebase.
2. Only after the full board build succeeds, run a supervised test on a spare XIAO with the same radio and microphone. Use the existing receiver. Capture a continuous serial transcript including `nzrt status`. Verify guard_online=1 and compare the same known signal with legacy active, shadow off versus shadow enabled. For a minimum 30-minute healthy-path gate enable WAV and exercise radio, journal and uploads. Check window progression, increasing DSP completions, no added dropped blocks, sequence-linked candidate/journal/WAV ACK, and inspect the actual received WAV. `py -3 bench_acceptance.py serial.txt` returns nonzero if the normal-path evidence is missing or unhealthy. This is not an automatic approval for field use.
3. In a **separate** fault test, disconnect the receiver and reproduce the signal; verify local candidate sequence advances. Reconnect; verify the backlog is reported when capacity permits, loss counts are visible and the journal is readable. Repeat with induced storage failures on a disposable bench filesystem. An absent/failed upload is not a negative call. A PC-side missed-heartbeat alert remains a separate next step.
4. Only consider field deployment after the full build, board/load/fault tests and a co-located night. Keep the existing PASS-1 binary/source rollback available. No SD firmware or Run Daily changes in this update.

Reproduce locally: `python test_gate.py` (native C++11); `python test_acceptance.py`; in the ESP-IDF 5.4.2 environment, `python run_emulator.py NEW_DIR --emu /path/to/esp-emu`. Automation pins esp-emu 0.50.0 by SHA-256. Source of the working tree is the PASS-1 release; any rebase that changes its five hashes requires updating the tests.

Reference: [ESP-IDF software reset](https://docs.espressif.com/projects/esp-idf/en/v4.4.7/esp32s3/api-reference/system/system.html) and [system watchdogs](https://docs.espressif.com/projects/esp-idf/en/v4.4.7/esp32s3/api-reference/system/wdts.html).
