# RT LIVE-1 field repair

The installed JOURNAL-4 recovered the damaged flash journal. In the 10 November hardware trace it emitted candidate 8, but the cumulative counters showed eight missed ML triggers, no completed clips, and no WAV acknowledgements. The trace does not establish whether that candidate reached the Windows receiver. A quiet dashboard cannot establish acoustic silence.

## Implementation

* Four files overlay the exact deployed source baseline. The original SHA-256 values are in hashes.json. WildlifeJournal.h remains the hardware-tested JOURNAL-4 version. Firmware identity is NZRT-J4-LIVE-1.
* DSP uses the same third-order CIC, bit order, 17-tap symmetric FIR coefficients, band, calibration and candidate scoring. Eight-bit moment tables replace single-bit integrator updates. The symmetric FIR uses eight paired products and a centre product. The DSP task runs one priority above the optional ML worker. The reader discards partial reads and marks continuity loss after RX overflow or failed reads. After four input gaps in one second, PCM collection for optional clips pauses until a continuous second of audio has passed. The band detector keeps evaluating acoustic windows. The clip_holds counter records each intervention. Three consecutive empty/error reads trigger an I2S restart attempt. Failed startup is retried every 30 seconds.
* The ML ring copies 128-sample batches into PSRAM. It flushes pending samples at trigger and gap boundaries, so the 250 ms pre-trigger and 1,750 ms post-trigger intervals keep their alignment. ML status distinguishes short pre-trigger history from occupied slots. A complete WAV remains eligible after inference failure or an auxiliary score journal failure. A gap-interrupted clip remains invalid.
* A candidate is printed to serial and queued independently for verified flash logging and RAM delivery. An interrupted journal write keeps the full batch for retry. The main loop sends short batches of complete candidate lines through the existing authenticated /rt-log endpoint during active monitoring or standby. Local journal failures and classifier/clip failures do not gate these transmissions. A batch is removed on HTTP 200 with the matching checksum response. Connection/POST failures retry after 30 seconds. The 64-event live queue keeps the newest events when full and counts displaced events. Journal snapshots still provide longer-term recovery after disconnection or restart. Snapshot files can overlap live batches. Session, run and sequence identify one event across copies.
* Periodic NZRT FIELD health=1 lines report active coverage and degraded intervals. NZRT LIVE reports outstanding, acknowledged and displaced candidates. CANDIDATE_SAVED is emitted only after a successful journal close. Health reports themselves can travel through /rt-log, including failures to initialise the microphone. Wi-Fi reports require configured Wi-Fi, a valid clock, a reachable receiver, and its existing token. Network work continues to use the main loop and can delay MeshCore servicing during HTTP operations. Test under real receiver and radio load.
* Recovery is bounded. A powered-down receiver cannot acknowledge an event. RAM delivery state is lost on reboot. A simultaneous prolonged storage and network outage can exceed both staging buffers. Any queue loss or persistently rising acquisition gaps means incomplete coverage.

## Windows deployment and acceptance

Start the existing extended receiver and close the serial monitor. Extract the package and run Repair_RT.cmd, or run it with a different port as its first argument and an existing project directory as its optional second argument. Default is COM8 and the project under %USERPROFILE%\NZRTAudioBatMonitor-meshcore\NZRT-MeshCore-NZBat-BandMonitor. This action applies the four source files with local backups, builds and uploads through the existing PlatformIO environment, and then starts a 210-second field check. Install uses the original four SHA-256 values to recognise the local source and can resume a partial update. Wi-Fi credentials and thresholds come from the existing project/device.

The field check opens serial, temporarily wakes capture, and restores the automatic schedule at the end. For a daylight check, present a known working ultrasonic acoustic source in the 18–45 kHz band as short bursts after the first 10 seconds. A controlled stimulus produces a genuine monitor record; keep its test time for exclusion from ecological analyses. Alternatively run field_check.py during naturally active hours. Ordinary PC speakers are unsuitable for a calibrated ultrasonic test.

The check compares session/run/seq on serial, in the verified journal-write receipt and in a checksum-verified receiver file. It also requires at least 95% of expected 20 ms windows, raw byte rates within 5% of 384,000 B/s, and advancing DSP work with no new queue drops, gaps, read errors or DMA overflow between active samples. WAV ACKs are reported separately. An absence of candidates makes this test inconclusive. For production acceptance, corroborate natural activity against the co-located AR4 over a full night and inspect queue loss, receiver files and WAVs. A brief replay or daylight check cannot establish field sensitivity.

Run the field check again without uploading using:

    py -3 field_check.py --port COM8

For a different Windows receiver folder append --receiver followed by the quoted WiFi_Backup directory. The script leaves a timestamped RT_field_*.log beside the installer when run by Repair_RT.cmd. To restore original sources run install.py with the same --project and --restore, then build/upload normally if the device should run JOURNAL-4 again.

## Reproducible developer checks

From this directory in the repository run python3 tests/replay.py and python3 tests/clip.py. The replay builds the production detector, exercises CIC equivalence through wraparound, processes MSB-first synthetic 36 kHz pulsed PDM, formats the candidate with firmware code, exercises a failed-delivery retry and queue overflow, checks that the production sender retains the batch across HTTP/status and bad-checksum failures, then submits the body twice to the reference receiver and checks its ACK and saved bytes. The HTTP client in this host test is Python. The clip test checks all 384,000 reference samples, wraparound, pre-trigger boundaries and gap invalidation.


## Validation on 11 November 2026 (NZ)

The detector emitted a score-100 candidate at 36.00 kHz from synthetic PDM. The production sender retained it after HTTP 503 and after an incorrect acknowledgement and removed it on the matching acknowledgement. The reference Windows receiver implementation (run locally) stored the complete formatted line and accepted a repeated POST. PCM comparison with the JOURNAL-4 detector covered 716,800 samples with a worst absolute difference of 1.79e-7 full scale. The WAV regression checked every sample in a 384,000-sample capture and gap invalidation. All 24 original JOURNAL-4 mock filesystem checks and the released receiver's three test groups passed. The field acceptance code rejected missing detections, missing journal receipts, invalid receiver digests and increasing gap counts.

The full NZRT_Xiao_S3_WIO_wildlife_repeater PlatformIO target compiled and linked with Espressif32 6.11.0 and Arduino 2.0.17 from a reconstructed project with a placeholder receiver configuration. Static RAM was 120,120 / 327,680 bytes. Flash was 1,279,953 / 3,342,336 bytes. Validation-only image SHA-256 was f270c89c2350f92b31928b5b1949c963bbbecf5d2515d97e3394ac2e21ef0252. The installer builds locally with the owner’s receiver configuration. The owner's RT, its acoustic input, Windows serial port, local receiver, overnight coverage and battery impact require field verification.

The RT log reader imported the synthetic candidate once across a live batch and a later snapshot, with no conflicts or unresolved records.
